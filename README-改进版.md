## 〇、先回答你最初的三个问题

### Q1：你的项目能自动每天收集网上的各种接口吗？

**改之前：不能。** 两个断裂点，我用 GitHub API 核实过：

| 环节 | 改之前的状态 | 证据 |
|---|---|---|
| 每天自动跑 | ❌ 完全没有 | 仓库里**没有 `.github/workflows/` 目录**，`/actions/workflows` 返回 `total_count: 0` |
| 真的跑过吗 | ❌ 一次都没有 | 4 个 commit 全是 `TVBox Backup <tvbox@example.com>` 人工提交，没有一条 bot 记录 |
| 自动发现新源 | ❌ 没有 | 输入只有 `apilinks.txt` 那几十行手写清单 |

### Q2：是否已经脱离原项目、能独立收集？

**部分脱离。而且有个你我都需要知道的事实：**

> **原项目 `lubin776/tvbox-api-backup` 根本没有「抓清单」这一步。**
> 它的 `api下载器.py` 里 `_load_api_config()` 只读**自己仓库里的** `api_list.json` / `api_list.py`（手写的），

所以「复刻原项目」这件事，能复刻的上限就是**「抓一份 API_LIST」**——
它本身也不是收集器，真正的收集必须自建。

## 一、目录结构

```
tvbox-agg-改进版/
├── .github/workflows/aggregate-daily.yml   ← 每日 04:00 自动跑（原来没有）
├── config/
│   ├── upstreams.txt          ← 收集层：接口清单源（改这里就能加来源）
│   └── liveupstreams.txt      ← 收集层：直播源清单
├── scripts/
│   ├── main.mjs               ← 入口
│   ├── collect.mjs            ← 收集层（原项目没有这层）
│   ├── tvbox.mjs              ← 配置解析 + 多仓递归 + 探活（含抗误杀）
│   ├── core.mjs               ← HTTP/解码/归一/去重键/测速分档
│   ├── pipeline.mjs           ← 筛选整理 + 分类 + 输出
│   └── selftest.mjs           ← 27 项离线自检
├── apilinks.txt               ← 人工种子（沿用你原来的格式）
├── data/
│   ├── pool.json              ← 发现池（自动维护，含来源与失败历史）
│   └── history.json           ← 每日统计历史
└── 聚合接口/                   ← 产物，文件名与原来完全一致
```

**注意：没有 `src/`（Next.js）、没有 `package.json`、没有任何 npm 依赖。**
脚本是零依赖 ESM，`node scripts/main.mjs` 直接跑。你原来那套 Next.js 数据库面板与每日聚合无关，
建议保留在你自己另一个仓库，别放进 Actions（否则 CI 要装 node_modules、连 Postgres）。

## 二、四个阶段做了什么

### 阶段 1：收集（原项目完全没有）

```
config/upstreams.txt  ─┐
config/liveupstreams.txt ─┼→ 抓取并抽地址 ─┐
apilinks.txt（人工种子）  ─┘                  ├→ data/pool.json（发现池）
已抓配置里的 urls/storeHouse（多仓）─────────┘        ↓
                                            按权重+失败次数挑候选
```

- 支持四种上游格式：`links`（名称,URL 文本）、`readme`（Markdown，**只看接口相关小节**）、`json`（递归抽 URL）、`apilinks`（你的格式）
- 抓到的候选写进 `data/pool.json`，记录**首次发现时间、来源、连续失败次数**
- 连续失败 ≥ `MAX_FAILS`（默认 3）轮才不再尝试 —— 避免临时抽风的源被永久丢掉
- 多仓递归挖到的子仓地址会**回写池子**，越跑池子越大

> 关于「自动发现」的诚实边界：本方案能在**公开代码仓 / 已收录配置的多仓结构**里自动找新源。
> 搜索引擎结果页、贴吧、QQ 群里的接口抓不到（Actions 访问不到也不稳定）。
> 任何声称「全自动收集全网所有接口」的说法都是夸大的——业界通行做法就是本项目这个水平。

### 阶段 2：筛选整理（去重 / 去失效 / 去低速）

**去重（4 类，比旧版更彻底）**

| 类型 | 旧版 | 新版 |
|---|---|---|
| 协议/www/末尾斜杠差异 | ✅ | ✅ |
| GitHub 代理前缀（`gh-proxy`/`ghproxy`/`jsdelivr` 等 12 个） | 部分 | ✅ 支持**多层套娃**，且 `jsdelivr@main` 与 `raw/main` 对齐 |
| `?ac=list` / `?ac=detail` 与裸地址 | ❌ 被当成两个站 | ✅ 归一（实测在你旧产物里能合并 12 组真实重复） |
| ext 内部 URL 的镜像差异 | ❌ | ✅ 递归归一 |

**去失效（按类型分策略，实测数据）**

| 类型 | 检测 | 本轮剔除 |
|---|---|---|
| 采集站 type 0/1 | `ac=list` → `ac=detail&pg=1` → 取首条 `vod_name` 做内容指纹 | 32 |
| Py 站 | 主文件 200 + 大小 + 含 `def/import` | 计入下方 |
| JS 站 | 主文件 + ext 规则文件双检 | 计入下方 |
| Jar 站 type 3 | jar 必须是 ZIP（`PK` 魔数）+ >10KB，**且** ext 里的目标站域名可达 | 156 |
| 全部 | 域名不存在 113、HTTP 错误 236、超时 154、内容异常 168 | — |
| 本机引用 | 含 `127.0.0.1`/`localhost` 的条目（对别人必然失效） | 305 |

**关键设计：抗误杀。** 实测发现最大的误杀源是 **HTTP 429（限流）**——
第一版直接把 429 当死站删掉，实测一轮里有 246 条因此被误删。
现在 `403/408/423/425/429/500/502/503/504/521/522/523` 全部按「**测不准**」处理：
退避重试 2 次 + 换 UA，仍失败则**降级保留**而不是删除。

**去低速**

- 三次取样，取**中位数**（避免网络抖动误杀）
- 判定用 `TTFB`（首字节）+ 吞吐 `KB/s` 两个维度
- **重要**：JS/Py/Jar 站真正决定用起来卡不卡的是 `ext` 里指向的**目标站域名**，不是规则文件本身。
  所以测速优先测目标站，规则文件只在没有 ext 时才测。
- 分档：`fast`（TTFB≤0.8s）/ `ok`（≤3s）/ `slow`（>3s 或吞吐<30KB/s）/ `dead`
- 输出时**快站排最前**，TVBox 里优先连好的

本轮实测分档：**精选 3,460 / 普通 241 / 偏慢 862 / 失效 1,593**

### 阶段 3：分类

输出文件与你原来**完全一致**，只是内容经过过滤：

| 文件 | 内容 |
|---|---|
| `点播-采集站.json` | type 0/1 |
| `点播-Py站.json` | `.py` 结尾 |
| `点播-JS站.json` | `.js` 结尾（含 ext 是 js 的） |
| `点播-Jar爬虫站.json` | type 3（`csp_*`） |
| `点播合集.json` | 以上全部合并去重，快站排前 |
| `live.json` | 直播源（按测速排序） |
| `live.m3u` | 频道归一合并后的播放列表 |
| `剔除报告.json` | **新增**：谁被删、为什么、实测多快 |
| `README.md` | **新增**：本次统计 |

### 阶段 4：输出

- 每个文件的站点数、直播数写进 `聚合接口/README.md` 与 Actions Summary
- 每轮统计追加到 `data/history.json`（保留 180 天），可以看到趋势
- **安全阀**：本轮站数低于上次的 `MIN_RATIO`（默认 50%）时**拒绝写文件**，防止上游集体故障把产物写空
  （你旧版的 `MIN_SITES = 100` 是绝对阈值，启用严格探活后几乎必然被触发，等于永远不更新）

## 三、直播整理（这次改动最大的部分之一）

**你旧版的问题**：`live.m3u` 95,141 条 / 15.7 MB，其中 17% 是 MV/音乐/公告，
一个 `MTV劲爆点歌仓库` 分组就占了 **16 万条**，一个 CCTV1 有 **402 个源**。

**现在的做法：**

1. **分组级过滤**：分组名命中 MV/音乐/点歌/MTV/劲爆/舞曲/歌手/演唱会/小品/相声 等关键词整组丢弃；
   单分组超过 `MAX_GROUP_CHANNELS`（默认 3000）整组丢弃（这是点歌台/影音库，不是电视直播）
   → 实测一轮剔除 **253 个噪组、536,700 条频道**
2. **频道名归一**：`CCTV1` / `CCTV-1` / `央视一套` / `CCTV1高清` → 同一频道；
   `湖南卫视高清` / `湖南卫视备用2` → `湖南卫视`；`CCTV5+` 不会被误并到 `CCTV5`
3. **每台保留 N 个源**（`LIVE_PER_CHANNEL`，默认 3），按源测速排序取最快的
4. **稳定排序**（分组+频道名），让每日 diff 尽量小，避免仓库体积膨胀
5. 直播源清单（`config/liveupstreams.txt`）直接提供整份频道列表，质量比从点播接口 `lives` 里捞的高

## 四、怎么用

### 本地跑

```bash
# 需要 Node 18+，不需要 npm install
node scripts/selftest.mjs           # 先跑离线自检（27 项）
node scripts/main.mjs --dry-run     # 只看会抓哪些源，不写文件
node scripts/main.mjs               # 真跑一轮
```

### 部署到你的仓库

```bash
# 1. 把本目录内容覆盖到你的仓库根
# 2. 确认 .github/workflows/aggregate-daily.yml 已提交
git add .github/workflows/aggregate-daily.yml scripts/ config/
git commit -m "feat: 补齐收集层 + 探活测速 + 每日定时"
git push

# 3. 到仓库 Actions 页面点一次「Run workflow」验证
```

**第一次必须在 Actions 页面手动点一次**，确认能跑通再等定时。

### 可调参数（全部走环境变量，不用改代码）

| 变量 | 默认 | 说明 |
|---|---|---|
| `STRICTNESS` | `strict` | `strict` 只留快站（默认，定时任务即此档）/ `balanced` 死站删·慢站留文末 / `loose` 只删死站 |
| `SLOW_TTFB_MS` | 1500 | 首字节超过这个判为慢（strict 下删除），中间一律算普通保留 |
| `FAST_TTFB_MS` | 300 | 低于算精选，排最前 |
| `CRAWLER_SLOW_TTFB_MS` | 3000 | 内置爬虫站（csp_*）放宽阈值，因为测的是目标站首页 |
| `KEEP_UNPROBED` | 1 | 预算用尽没测到的站标 `unsure` 保留，下轮补测（0=当死站丢弃） |
| `MAX_FAILS` | 3 | 连续失败几轮才永久剔除 |
| `LIVE_PER_CHANNEL` | 3 | 每个频道保留几个源 |
| `FILTER_NON_TV` | 1 | 过滤 MV/音乐/点歌台 |
| `MAX_GROUP_CHANNELS` | 3000 | 单分组超量整体丢弃 |
| `DROP_LOCAL_REF` | 1 | 去掉 127.0.0.1 引用 |
| `KEEP_SOURCE_SUFFIX` | 0 | 名字是否加「｜来源」 |
| `MAX_CANDIDATES` | 600 | 本轮最多抓多少候选 |
| `BUDGET_FETCH` / `BUDGET_PROBE` / `BUDGET_LIVE` | 900/1560/600 | 分阶段预算（秒），到点收工绝不拖超时 |
| `MIN_RATIO` | 0.5 | 结果低于上次这个比例就拒绝覆盖 |
| `HISTORY_KEEP_DAYS` | 30 | 历史统计保留天数（产物本身每天覆盖，不累积） |
| `POOL_KEEP_DAYS` | 30 | 候选池保留天数，30 天没出现的地址自动清掉 |

### 加收集来源

编辑 `config/upstreams.txt`，加一行：

```
来源名, https://raw.githubusercontent.com/owner/repo/main/xxx.txt, links
```

类型可选 `links` / `readme` / `json` / `apilinks`。跑一次 `--dry-run` 就知道抽到多少条。

## 六、诚实说明与已知限制

1. **GitHub Actions 定时不保证准点**，高峰期可能延迟 5~30 分钟。
2. **仓库连续 60 天无 commit 会自动暂停定时任务**；本项目每天有 commit，不受影响。
3. **接口站失效是常态**，日掉 10~20% 属正常。这正是「自动收集」必须存在的理由。
4. **探活只能验证「配置/规则文件能下载」**，无法验证某个影视源是否还有片源版权内容——
   那需要真正调用 TVBox 的 spider 逻辑，Node 环境做不到（需要 JVM 跑 jar）。所以 jar 站的判定是
   「jar 完整 + 目标站可达」，属于**尽力而为**的存活判断。
5. **`csp_*` 内置爬虫站**（api 不是 URL）无法探活，只能信任——这部分会原样保留。
6. 本次实测环境是沙盒（境外网络），**国内网络的实际速度分档会不同**，
   所以测速阈值都做成了环境变量，你可以在 Actions 里按国内情况调。
