# ===== 收集层：直播源清单（种子） =====
# 每行：「名称, URL, 类型」
#   类型：txt = 「名称,地址」或「#genre#」分组格式；m3u = M3U 播放列表
#
# 这些源会像普通 lives 一样被抓取、解析成频道，参与「频道归一合并」，
# 频道级去重 + 每台保留 N 个源 之后再输出到 live.m3u。
# 好处：它们是已经过别人测速筛过的，比从点播接口 lives 里捞出来的杂乱源质量高。
#
# ===== 种子的三个特权（scripts/pipeline.mjs 的 mergeLiveSeeds）=====
#   1. 排在探活队列最前 —— pool 按顺序派活，直播预算不够时先保证种子被测到
#   2. 内容哈希去重「先到先得」，种子优先当正本，与它内容相同的杂源被剔
#   3. 不受本轮直播预算（BUDGET_LIVE）限制，绝不会因为「预算用尽」被判死
#   同一个地址如果点播接口的 lives 里也有，就地升级成种子（不重复计一条）。
#   被剔的种子会在 聚合接口/剔除报告.json 里带「（直播源清单种子）」标记，方便复查。
#
# ⚠️ 这里只能放**播放列表**。多仓/接口索引 JSON（形如 {"urls":[{"url":...}]}）
#    解析不出频道，脚本会直接拒绝并提示；那类清单属于点播收集层，
#    请放进 config/upstreams.txt 用 json 类型。（Supprise0901 的 warehouse.txt
#    就是这种，2026-11-22 已挪走。）
#
# 收录标准（缺一不收，避免每天白测）：
#   · GitHub 上的：用 api.github.com 确认文件存在且体积正常（见每行注释的实测大小）
#   · 站内的：以 lubin776/tvbox-api-backup 的 livelist.txt 为交叉验证 —— 那里第五列是
#     来源线路、第二列是下载日期，只收「当天成功下载且体积正常」的（它的 CI 每天北京 03:00 跑）
#   · 明显是 MV/音乐/点歌台的（如 8MB 的「音乐所.txt」）不收：分组过滤会把它们全丢掉，白占带宽
